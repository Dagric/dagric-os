# Dagric GitHub growth audit

Audit date: 2026-09-04
Repository: https://github.com/Dagric/dagric-os

## Baseline

The public repository showed 0 stars, 0 watchers, 0 forks, and 0 open issues.
GitHub's available 14-day traffic window reported 1 repository view from 1
unique visitor, 56 clones from 38 unique cloners, no recorded referrers, and one
popular content path. Clone traffic without comparable page views may include
automation and should not be treated as an audience count.

The live repository had a good description and homepage, five broad topics, a
strong signed release record, and 328 commits. Its community profile was only
28% because it exposed a README but no recognized license, contribution guide,
code of conduct, security policy, issue templates, or pull-request template.

## What was improved

- Added the repository's license and rights documents.
- Added contribution, conduct, support, and security policies.
- Added structured bug, feature, and real-hardware report forms.
- Added a pull-request template and monthly dependency update configuration.
- Added a visual README header, status badges, clear Free-download actions, and
  a concise “ways to help” section.
- Expanded topics around desktop Linux, Windows migration, privacy, Btrfs,
  Secure Boot, Calamares, and beginners.
- Enabled GitHub Discussions, secret scanning, and push protection.
- Added a cross-platform rights preflight for local and future CI use. A new
  GitHub Actions check was tested but removed from this focused change because
  the account's jobs are currently prevented from starting by a billing lock;
  displaying that infrastructure failure as a product-quality failure would be
  misleading.

## Attention plan that does not manufacture engagement

1. Publish one pinned “Start here” Discussion linking the Free download,
   verification record, current limitations, and three ways to help.
2. Label five small, evidence-based issues as `good first issue`; documentation,
   translations, hardware-report formatting, and test fixtures are ideal.
3. Share a current continuous product demonstration that links directly to the
   verified GitHub release—not the repository homepage alone.
4. Ask real testers for structured hardware reports through the new form. Never
   buy stars, trade stars, or create fake accounts; those numbers do not produce
   users or trust.
5. Publish short release notes for meaningful changes and keep old automatic
   releases clearly marked as superseded.
6. Add a current social-preview image in Repository settings after the next
   installed-system capture. It should show a clean Dagric feature, not virtual
   machine controls, the installer icon, or a generic logo-only wallpaper.
7. Review GitHub traffic weekly by source, visitor, release click, and Free
   download conversion. Stars are supporting evidence, not the business goal.

## Success measures

- GitHub unique visitors and release-page visitors
- Clicks to the verified Free download
- Verified Free downloads and successful hash checks
- New Discussions answered within two business days
- Actionable real-hardware reports
- Outside contributors who complete a merged documentation, test, or code change
- Reviewers who independently reproduce a release claim

Do not claim growth from clone counts alone, and do not publish revenue or
conversion claims until the measurement source is documented.
