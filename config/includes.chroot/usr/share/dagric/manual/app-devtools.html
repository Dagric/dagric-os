For developers

Git, compilers and PythonPRO

The toolchain is already there. No installers, no PATH surgery.

On Windows this wasVisual Studio Build Tools, Git for Windows, python.org installers
This one is part of Dagric OS Pro. You are reading the manual on the free edition, so it is not installed on this computer. The page is here on purpose — you should be able to see exactly what Pro adds before you decide whether you want it.

What it is

Dagric OS Pro arrives with git, build-essential (GCC, make and the C library headers) and Python with pip and venv. Nothing to download, nothing to add to a PATH, and a C program compiles in a fresh terminal on the first evening.

No editor is bundled. Kate is a capable one; VS Code, VSCodium, Zed, the JetBrains tools and the rest are all a search away in Discover.

Five things you will actually do

  1. Tell git who you are

    git config --global user.name "Your Name" and git config --global user.email "you@example.com". Do this once, before your first commit, or you will be renaming authors later.

  2. Make an SSH key for GitHub or GitLab

    ssh-keygen -t ed25519 -C "you@example.com", press Enter through the prompts, then paste the contents of ~/.ssh/id_ed25519.pub into the site's SSH keys page. Never share the file without .pub.

  3. Use a Python virtual environment

    python3 -m venv .venv then source .venv/bin/activate. Install packages with pip install inside it. Read the surprise below — on Debian this is not optional advice.

  4. Build something from source

    The usual ./configure && make && sudo make install works, but prefer checkinstall or a local prefix: software installed outside the package manager is software the package manager cannot update or remove.

  5. Get a library's development headers

    sudo apt install libfoo-dev. Debian splits libraries into a runtime package and a -dev package with the headers; a build that fails on a missing .h file almost always wants the latter.

One thing that will surprise you

pip install outside a virtual environment will be refused. You will see error: externally-managed-environment. This is deliberate and it is protecting you: the system Python belongs to Debian, and letting pip overwrite parts of it is a well-known way to break your desktop, since a great deal of the system is written in Python.

The answer is a venv per project, or pipx for command-line tools you want available everywhere. The --break-system-packages flag exists, is named honestly, and should be left alone.
